# 用戶空間驅動程式 {#userspace}

## 從用戶空間控制硬體 {#userspace_control}

SPDK 的大部分文檔都談論 _用戶空間驅動程式_，因此了解
這在技術層面上的含義非常重要。首先，
_驅動程式_ 是直接控制連接到計算機的特定設備的軟體。
其次，操作系統根據特權級別將系統的
虛擬記憶體分為兩類地址 -
[內核空間和用戶空間](https://en.wikipedia.org/wiki/User_space)。這種
分離由 CPU 本身的功能輔助，這些功能強制執行記憶體
分離，稱為
[保護環](https://en.wikipedia.org/wiki/Protection_ring)。通常，
驅動程式在內核空間中運行（即 x86 上的 ring 0）。SPDK 包含的驅動程式
相反，它們被設計為在用戶空間中運行，但它們仍然直接
與它們正在控制的硬體設備進行介面交互。

為了讓 SPDK 控制設備，它必須首先指示
操作系統放棄控制。這通常被稱為從設備解綁
內核驅動程式，在 Linux 上通過
[寫入 sysfs 中的文件](https://lwn.net/Articles/143397/) 來完成。
SPDK 然後將驅動程式重新綁定到與 Linux 一起打包的兩個特殊設備驅動程式之一 -
[uio](https://www.kernel.org/doc/html/latest/driver-api/uio-howto.html) 或
[vfio](https://www.kernel.org/doc/Documentation/vfio.txt)。這兩個驅動程式
在某種意義上是"虛擬"驅動程式，它們主要向操作
系統指示設備已綁定驅動程式，因此它不會自動嘗試
重新綁定預設驅動程式。它們實際上不會以任何方式初始化硬體，
甚至不理解它是什麼類型的設備。uio 和 vfio 之間的主要
區別在於 vfio 能夠編程平台的[IOMMU](https://en.wikipedia.org/wiki/Input%E2%80%93output_memory_management_unit)，
這是確保用戶空間
驅動程式中記憶體安全的關鍵硬體組件。有關完整詳細資訊，請參閱 @ref memory。

一旦設備從操作系統內核解綁，操作
系統就無法再使用它。例如，如果您在 Linux 上解綁 NVMe 設備，
對應於它的設備（如 /dev/nvme0n1）將消失。這進一步
意味著掛載在設備上的文件系統也將被移除，內核
文件系統無法再與設備交互。實際上，整個內核
塊存儲堆棧不再參與。相反，SPDK 提供了重新構想的
典型操作系統存儲
堆棧中大多數層的實現，全部作為可以直接嵌入到您的應用程式中的 C 函式庫。
這主要包括 [塊設備抽象層](@ref bdev)，但也包括
[塊分配器](@ref blob)。

用戶空間驅動程式利用 uio 或 vfio 中的功能將設備的
[PCI BAR](https://en.wikipedia.org/wiki/PCI_configuration_space) 映射到
當前進程，這允許驅動程式直接執行
[MMIO](https://en.wikipedia.org/wiki/Memory-mapped_I/O)。例如，SPDK @ref
nvme 映射 NVMe 設備的 BAR，然後遵循
[NVMe 規範](http://nvmexpress.org/wp-content/uploads/NVM_Express_Revision_1.3.pdf)
來初始化設備、創建隊列對，並最終發送 I/O。

## 中斷 {#userspace_interrupts}

SPDK 輪詢設備以獲取完成狀態，而不是等待中斷。這樣做
有許多原因：1) 實際上，將中斷路由到
用戶空間進程中的處理程序對於大多數
硬體設計來說是不可行的，2) 中斷會引入軟體抖動，並且由於強制上下文切換而具有顯著的
開銷。SPDK 中的操作幾乎
都是異步的，允許用戶在
完成時提供回調。回調在響應用戶調用函數
輪詢完成時被調用。輪詢 NVMe 設備很快，因為只需要讀取主機
記憶體（無 MMIO）來檢查隊列對是否有位翻轉，並且
諸如 Intel 的
[DDIO](https://www.intel.com/content/www/us/en/io/data-direct-i-o-technology.html)
等技術將確保正在檢查的主機記憶體在設備更新後存在於 CPU 快取中。

## 線程 {#userspace_threading}

NVMe 設備公開多個隊列，用於向硬體提交請求。
可以無協調地訪問單獨的隊列，因此軟體可以從多個執行線程並行地向設備發送
請求，而無需
鎖。不幸的是，內核驅動程式必須設計為處理來自
操作系統中許多不同位置或系統上各種
進程的 I/O，並且這些進程的線程拓撲會隨著
時間而改變。大多數內核驅動程式選擇將硬體隊列映射到核心（盡可能接近
1:1），然後當提交請求時，它們查找
當前線程碰巧運行的任何核心的正確硬體隊列。
通常，它們需要圍繞隊列獲取鎖或
暫時禁用中斷以防止來自運行在同一核心上的線程的搶占，
這可能很昂貴。這是相對於只有單個隊列或根本沒有隊列的舊硬體介面的重大改進，
但仍然不總是最優的。

另一方面，用戶空間驅動程式嵌入到單個應用程式中。
該應用程式確切知道存在多少線程（或進程），
因為應用程式創建了它們。因此，SPDK 驅動程式選擇
直接向應用程式公開硬體隊列，要求
硬體隊列一次只能從一個線程訪問。在
實踐中，應用程式為每個線程分配一個硬體隊列（與
內核驅動程式中的每個核心一個硬體隊列相反）。這保證了線程
可以提交請求，而無需與系統中的其他線程執行任何類型的協調（即
鎖定）。
